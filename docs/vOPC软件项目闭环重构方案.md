# vOPC 软件项目闭环重构方案

> 状态：待人审
> 日期：2026-09-01
> 依据：`docs/wxx-vopc-prd-v2.0.md`
> 目标：以“软件与 AI 产品”模板跑通团队组建、G0–G4 阶段推进、阶段成果、模拟反馈和复盘结项的完整教学闭环。

## 1. 重构原则

1. 遵循 PRD v2.0 的 L1–L3 教学定位，不把模拟演示包装成真实 AI 执行或真实软件上线。
2. 软件项目主理人仍是第一责任人；虚拟团队负责模板化提示，不能代替人工确认、里程碑评审和风险审批。
3. 自动组队与手工组队共用同一套项目团队模型，后续可随时调整。
4. G0–G4 每阶段必须展示目标、负责人、任务、产出、证据、门禁和下一步，形成可回退、可审阅、可存档闭环。
5. 演示数据必须显著标记“模拟”，与真实项目、真实成员、真实反馈隔离。
6. 复用现有项目、成员、虚拟向导、任务、成果版本、决策、里程碑、风险、结项和审计能力，不另建重复业务系统。

## 2. 当前实现与主要缺口

### 已具备

- G0–G4 项目阶段、项目状态机和阶段进度条。
- 创建项目时自动生成 4 个虚拟向导岗位。
- 真人成员邀请、任务、决策、成果及版本、里程碑评审。
- 风险治理、结项/暂停/转向/终止/归档、虚拟向导稿及人工审阅。
- L1 入门、项目大厅、成果与复盘汇总。

### 缺口

1. 自动组队是后端固定插入 4 个岗位，用户看不到组队依据，无法在创建时预览或调整。
2. 手工组队仅有“邀请成员”，不能以软件团队岗位为中心配置真人/虚拟向导/空缺岗位。
3. 项目工作台按功能纵向堆叠，缺少“当前阶段驾驶舱”，用户不清楚此刻应做什么、完成到哪里。
4. 阶段只展示 G0–G4 标识，没有阶段目标、责任岗位、检查项、成果、门禁结果和历史事件。
5. 缺少可重复的一键模拟演示，无法直观看到软件项目从想法到复盘的全过程。
6. G3 模拟用户反馈和 G4 复盘虽然可由现有记录承载，但入口分散，未形成连续流程。

## 3. 目标用户流程

```text
进入 vOPC
  → 选择“软件与 AI 产品”
  → 选择项目方式：空白项目 / 模拟演示
  → 填写 G0 想法卡
  → 选择组队方式：自动组队 / 手工组队
  → 确认团队章程
  → G1 目标与方案
  → G2 任务执行与阶段成果
  → G3 模拟验证与反馈
  → G4 复盘并选择结项 / 转向 / 暂停 / 终止
  → 生成成果包和过程时间线
```

## 4. 软件项目团队模型

### 4.1 默认岗位模板

| 岗位 | 默认承载方式 | 核心职责 | 主要阶段 |
|---|---|---|---|
| 主理人 / 产品负责人 | 当前用户 | 目标、范围、决策、最终确认 | G0–G4 |
| 产品经理向导 | 虚拟向导 | 用户问题、需求、验收标准 | G0–G3 |
| 架构与后端向导 | 虚拟向导 | 技术方案、接口、数据设计 | G1–G2 |
| 前端体验向导 | 虚拟向导 | 页面流程、交互、演示界面 | G1–G2 |
| 测试质量向导 | 虚拟向导 | 测试清单、缺陷、验证结论 | G2–G3 |
| 交付复盘向导 | 虚拟向导 | 发布清单、成果包、复盘模板 | G3–G4 |
| 真人协作者 | 可选 | 承接指定岗位或任务 | G1–G4 |
| 导师/评审 | 可选真人 | 点评、里程碑通过或退回 | G1–G4 |

### 4.2 自动组队

- 根据 `project_type=软件与 AI 产品` 和 G0 想法卡生成推荐岗位。
- 默认创建 5 个软件项目虚拟向导岗位；如项目涉及 AI、数据或移动端，再显示可选岗位。
- 组队确认页展示每个岗位的职责、参与阶段和首个建议任务。
- 主理人可在确认前禁用非必要岗位，确认后仍可调整。
- 自动组队只生成模板岗位和任务草案，不调用真实模型，不虚构真人成员。

### 4.3 手工组队

- 以“岗位卡”而非单纯用户列表组队。
- 每个岗位可选择：当前用户兼任、邀请真人、使用虚拟向导、暂时空缺。
- 邀请真人继续复用学院准入、项目成员关系和邀请确认机制。
- 同一真人可兼任多个岗位，但 UI 给出负载提示；不强制阻止。
- 评审岗位必须与里程碑评审权限和项目成员关系一致，不能由前端伪造。

### 4.4 推荐数据调整

复用 `vopc_ai_roles` 与 `vopc_project_members`，增量增加：

- `vopc_projects.team_mode`：`auto/manual`。
- `vopc_projects.is_demo`：是否模拟演示项目。
- `vopc_ai_roles.responsible_stages`：如 `["G1","G2"]`。
- `vopc_ai_roles.responsibilities`：岗位职责说明。
- `vopc_ai_roles.sort_order`：团队展示顺序。
- 新表 `vopc_team_assignments`：岗位与真人/主理人/虚拟向导的统一映射，保留历史变更和审计。

不删除现有 `vopc_ai_roles` 或 `vopc_project_members`，保证历史项目兼容。

## 5. G0–G4 阶段驾驶舱

### G0 想法

- 输入：问题、目标用户、价值假设、软件形态。
- 团队动作：选择自动/手工组队并确认团队章程。
- 输出：想法卡、团队快照。
- 门禁：必填信息完整，主理人确认。

### G1 目标与方案

- 输入：目标卡、范围、不做清单、验收标准、技术/交互方案。
- 团队动作：产品、架构、前端向导各给出模板化检查清单；主理人接受、修改或退回。
- 输出：方案卡、关键决策、初始任务清单。
- 门禁：方案成果版本 + 决策记录 + 主理人/评审确认。

### G2 执行与产出

- 输入：阶段任务、负责人、截止时间、验收标准。
- 团队动作：任务看板按待办/进行中/待验收/完成展示；虚拟向导仅生成草稿。
- 输出：需求说明、原型/页面说明、接口或数据说明、测试记录、演示成果版本。
- 门禁：至少一个有效成果版本，任务满足验收要求，提交正式里程碑。

### G3 验证与反馈

- 输入：模拟用户、场景、反馈内容、验证假设、缺陷与改进项。
- 团队动作：测试质量向导提供检查模板；主理人录入或由演示脚本生成明确标记的模拟反馈。
- 输出：反馈记录、验证结论、改进任务、是否满足目标。
- 门禁：反馈表完整；R2/R3 风险未审批时不得推进。

### G4 复盘与闭环

- 输入：成果摘要、目标达成、有效做法、问题、经验、下一步。
- 团队动作：交付复盘向导生成结构化复盘草稿，主理人审阅。
- 输出：复盘报告、成果包、完整时间线。
- 决策：结项 / 转向 / 暂停 / 终止；所有路径都要求理由并写审计。

## 6. 页面重构

### 6.1 vOPC 首页

- 主操作改为“创建软件项目”和“运行模拟演示”。
- 项目卡增加：团队模式、当前阶段完成度、下一步、模拟标记。
- 保留 L1 入门、项目大厅、成果与复盘。

### 6.2 创建向导

四步 Stepper：

1. 选择模板：软件项目 / 其他项目。
2. 填写 G0 想法卡。
3. 选择自动组队 / 手工组队并配置岗位。
4. 预览项目、团队与 G0 交付物后创建。

### 6.3 项目工作台

顶部固定：项目、模拟标识、G0–G4 阶段轨道、总体完成度、当前风险。

工作区采用 6 个页签：

1. **当前阶段**：目标、检查项、责任岗位、下一步主按钮。
2. **团队**：组织图、岗位、真人/向导/空缺、邀请和调整。
3. **任务**：阶段任务看板。
4. **成果**：成果与版本、阶段证据。
5. **验证**：反馈、风险、里程碑评审。
6. **复盘**：结项路径、时间线、成果包。

高级治理能力按需折叠，不再把所有表单一次性堆在页面中。

## 7. 模拟演示

### 7.1 演示项目

内置“校园活动报名小程序”软件项目案例；全部数据标记 `is_demo=true`、`source=simulation`。

### 7.2 演示方式

- **分步演示**：用户点击“推进下一步”，系统展示本阶段团队动作，再生成结构化模拟记录。
- **自动播放**：每 1–2 秒推进一条只读演示事件，可暂停、继续、重新开始。
- 自动播放只改变演示项目的模拟记录，不自动冒充导师评审、不绕过风险审批。
- 需要人工确认的节点停在“等待主理人确认”，用户点击后继续。

### 7.3 演示事件

```text
创建想法卡
→ 自动组建软件项目团队
→ 产品向导生成需求清单
→ 架构/前端向导形成方案草稿
→ 创建并完成模拟任务
→ 登记演示成果 v0.1
→ 生成 3 条模拟用户反馈
→ 创建改进任务并登记 v0.2
→ 完成复盘
→ 主理人选择结项
```

### 7.4 数据与接口

新增：

- `POST /api/v1/vopc/demo-projects`：创建隔离的演示项目。
- `POST /api/v1/vopc/projects/:id/simulation/advance`：推进一个演示事件。
- `POST /api/v1/vopc/projects/:id/simulation/reset`：重置演示。
- `GET /api/v1/vopc/projects/:id/timeline`：统一返回项目阶段事件时间线。
- 新表 `vopc_simulation_runs`、`vopc_simulation_events`；事件写入时同时保留 vOPC 审计。

所有演示接口必须校验：项目属于当前用户、`is_demo=true`、学院准入有效。

## 8. 闭环判定

软件项目被视为“走通闭环”需同时满足：

1. G0 想法卡完整且团队已确认；
2. G1 有目标/方案成果和关键决策；
3. G2 有任务及至少一个有效成果版本；
4. G3 有反馈记录、验证结论和改进项；
5. G4 有复盘报告及明确的结项/转向/暂停/终止决定；
6. R2/R3 风险门禁有效；
7. 阶段推进、团队变化、向导草稿审阅、成果版本和闭环决定均可在时间线追溯。

## 9. 实施增量

### 增量 A：团队组建闭环

- 迁移团队模式、演示标记、岗位职责和岗位分配。
- 自动组队服务、手工岗位配置 API。
- 创建向导和团队组织图。
- 测试：自动模板、手工岗位、真人邀请、越权、学院隔离。

### 增量 B：阶段驾驶舱

- 阶段摘要 API，聚合任务、成果、反馈、风险和门禁。
- G0–G4 阶段轨道、当前阶段页签、下一步动作。
- 测试：阶段完成度、空态、回退、风险冻结、历史项目兼容。

### 增量 C：模拟演示

- 演示项目、演示运行及事件表。
- 分步推进、暂停/继续/重置和时间线 UI。
- 测试：确定性、幂等、仅演示项目可推进、不可冒充评审、数据隔离。

### 增量 D：闭环验收

- G3 反馈与 G4 复盘专用 UI。
- 成果包与完整时间线。
- 后端全量测试、Flutter analyze/test/build、Web 演示验收。

每个增量均执行：文档更新 → Go build/vet/test → Flutter analyze/test/build → Git 中文提交 → 推送。

## 10. 模拟验收剧本

1. 学生进入 vOPC，点击“运行模拟演示”。
2. 系统创建“校园活动报名小程序（模拟）”。
3. 选择自动组队，展示 5 个虚拟岗位及主理人责任。
4. 分步推进 G0–G1，用户修改并接受一份需求草稿。
5. G2 展示任务看板，形成 v0.1 演示成果。
6. G3 生成明确标记的模拟反馈，创建改进任务并形成 v0.2。
7. G4 展示目标达成、经验和风险，用户选择结项。
8. 成果页显示团队快照、阶段成果、反馈、复盘和完整时间线。
9. 新建空白软件项目，选择手工组队，邀请真人协作者并配置虚拟向导。
10. 非成员访问私有项目、非演示项目调用模拟推进、外院用户访问均被服务端拒绝。

## 11. 人审决策点

建议采用以下默认方案：

- 团队：自动组队默认 5 个虚拟岗位，允许创建前删减；真人成员可后续替换岗位。
- 演示：采用内置“校园活动报名小程序”，分步演示为默认，自动播放为辅助。
- 推进：演示可自动生成记录，但所有主理人确认、正式评审和风险审批节点必须停下等待人工操作。
- 范围：本期只完成 L1–L3 教学闭环，不接真实代码代理、真实部署或真实经营能力。
