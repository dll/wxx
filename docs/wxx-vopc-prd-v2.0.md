## 0. 为什么重构（v2.0 的动机）

v1.0 把 vOPC 设计成"尽可能贴近真实公司经营"的孵化平台：S0–S9 十个阶段、公司成立、真实 AI 虚拟员工执行、云对象存储、病毒扫描、真实支付/合同/税务、多端/WebView、P95 压测与备份恢复。上线验收（SAR v1.0）明确 **NO-GO**：其中大量 P0 依赖真实运行环境（模型 API、对象存储与凭据、生产同构 MySQL/Turso、真机多端），**当前项目不具备这些环境条件，无法实现**。

**重构核心思想（一句话）：**

> **vOPC 是一个"虚拟化"的 OPC 教学模块——用"分层复杂度"让用户理解 OPC（一人公司）的流程与核心思想，掌握"一个人如何像一家公司一样把想法推进为成果"即可。它是蔚小芯的一个业务模块，不追求复刻真实公司流程。**

- **虚拟化** = 公司组织、岗位、团队、流程都在模块内"模拟运行"，不触碰真实公司在环境上做不到的部分。
- **分级** = 把 OPC 的复杂性拆成清晰的抽象层级，用户可按自己的理解阶段进入，每一层都能"掌握这一层的核心思想"。
- **可落地** = 去掉依赖真实运行环境/凭据的高度现实主义设计，只保留当前环境能跑通的闭环，把"过于真实"的部分降级为远期架构预留（不实现）。

本版不否定 v1.0 的建设目标（让人具备提出想法、组织虚拟团队、做出成果、承担决策的能力），但**把交付标准从"真实公司经营/真实产品上线"下调为"理解 OPC 核心思想并跑通一条受控的虚拟主线流程"**。

## 1. 一句话定位（v2.0）

**vOPC 是蔚小芯的一个虚拟 OPC 教学模块：用户以"一人公司主理人"身份，通过四个依次递进的复杂度层级（概念层→流程层→闭环层→现实预留层），用"虚拟 AI 团队"辅助，把一个小想法走通"需求→成果→反馈→复盘"，从而掌握 OPC 的核心思想。它不要求真实上线、真实经营或真实公司流程，也不依赖真实 AI 执行环境。**

---

## 2. 分层模型（本版核心设计）

把 OPC 的复杂性抽象为 **L1–L4 四个层级**。每一层都有明确的学习目标和可运行的交付物，**用户可以从任意一层进入**，不强制必须走满更高层。层级之间是"递进理解"，而不是"必过的审批流水线"。

### L1 · 概念层（认识 OPC 核心思想）
- **要解决的问题**：OPC 到底是什么？一人公司为什么成立？
- **学习目标**：理解"一个 OPC ≈ 需求方 + 产品/服务 + 交付 + 反馈"的最小闭环；明白 OPC 强调"一个人要承担产品、市场、交付等多数角色"。
- **用户做什么**：阅读/观看 OPC 核心知识卡，走完一张"OPC 核心流程图"（idea → validate → build → deliver → feedback）。
- **可运行交付物**：讲解内容、核心流程图、自测小问卷。**无需任何项目、团队或外部环境。**
- **状态**：**本期实现**（纯内容 + 交互，零环境依赖）。

### L2 · 流程层（跑通一条业务主线）
- **要解决的问题**：OPC 是如何一步步把想法变成果的？
- **学习目标**：掌握 OPC 的主线流程（需求→目标→方案→成果→反馈），能自己走通一条受控的虚拟主线。
- **用户做什么**：以主理人身份创建一个"虚拟练习项目"，按**精简版阶段**（见 §5）逐步走通；"虚拟 AI 团队"以**模板化向导**形式逐环节提供引导（清单、模板、角色扮演提示），帮助理解每个角色在做什么。
- **可运行交付物**：一个可审阅、可回退、可存档的虚拟项目记录（含任务、产出、决策、里程碑）。所有产出为结构化文本，**不需要真实模型执行、云存储或外部凭据**。
- **状态**：**本期实现**。

### L3 · 闭环层（掌握 OPC 完整生命周期）
- **要解决的问题**：OPC 从创意到复盘、升级或终止的完整闭环怎么运转？
- **学习目标**：掌握 OPC 的完整生命周期，包括里程碑门禁、风险分级、结项/终止/复盘、成果归档与展示。
- **用户做什么**：在 L2 虚拟项目的基础上，加入结项状态机、里程碑评审、风险治理、成果仓库与复盘；项目可以"结项""暂停""转向""终止"，每一条路径都有依据与复盘。
- **可运行交付物**：完整生命周期闭环 + 成果包导出 + 复盘报告。**当前环境可完整实现，是本版功能的"现实边界"（不做真实金融/合同/云存储/真 AI 执行）。**
- **状态**：**本期实现（沿用 v1.0 已实现的安全门禁、状态机、风险治理骨架）**。

### L4 · 现实延伸层（远期预留，本期不实现）
- **要解决的问题**：如果未来有条件，vOPC 能否对接真实的 AI 执行、对象存储与真实经营？
- **学习目标**：架构上为"真实化延伸"预留接口，但**明确本期不做**。
- **用户做什么**：无（本期无用户出口）。
- **预留给远期的能力**（仅架构预留点，不实现）：真实模型 API 执行与上下文隔离、云对象存储 + 病毒扫描 + 签名 URL、真实 MySQL/Turso 生产同构升级、多端/WebView、P95 压测、备份恢复演练、真实支付/合同/税务/结算。
- **状态**：**本期不实现**，只在数据模型与代码分层上保留扩展位，避免"过于真实的公司流程"拖累核心闭环落地。

> **为什么这样分：** v1.0 的失败在于把最难的"现实延伸层"当作 P0 必须项。v2.0 把它们降为 L4 且明确不实现，把教育主线（L1–L3）作为本期交付——用户真正需要掌握的是 OPC 的核心思想与主线流程，而不是真实跑一家公司。

## 3. 产品属性（v2.0 收敛）

| 属性 | v1.0 描述 | v2.0 收敛 |
|---|---|---|
| 虚拟公司经营环境 | 模拟线下真实公司运作 | **虚拟化**：公司/岗位/流程仅在模块内模拟，不追求真实公司流程 |

| AI 协作平台 | 用户管理真实 AI 虚拟员工 | **模板化向导**：以引导/清单辅助理解角色，不用真实模型执行 |
| 孵化基地 | 需求→研发→生产→运维完整闭环 | 收敛为 **L3 生命周期闭环**，真实生产/运维降为 L4 预留 |

## 4. 用户与角色（沿用 v1.0 边界，简化项目角色）

### 4.1 使用范围（沿用）
仅限计算机学院范围内已授权的蔚小芯用户；外院、校外、游客不可进入。三层学院范围校验（前端入口、后端接口、数据查询）作为唯一硬边界保留。

### 4.2 平台身份与项目身份分离（沿用）
用户系统角色与项目角色分离，同一用户可在不同项目担任不同角色。

### 4.3 项目角色（v2.0 简化为三类 + 一个只读辅导角色）
| 角色 | 职责 | 核心权限 |
|---|---|---|
| OPC 主理人 | 项目第一责任人；掌握 OPC 决策 | 创建项目、走流程、提交里程碑、结项/复盘 |
| 协作者（真人） | 可选；陪练/分担任务 | 查看项目、执行任务、上传虚拟产出、讨论 |
| 虚拟向导（原"AI 虚拟员工"） | 按环节给模板化引导/清单 | 在授权范围内读取项目上下文、产出结构化建议 |
| 辅导/评审（导师或评审者） | 点评、里程碑评审（可选） | 查看授权内容、点评、通过或退回 |

> **虚拟向导（v2.0 对 v1.0 "AI 虚拟员工"的重构）：** 不依赖真实模型执行。它以"流程角色 + 模板 + 清单 + 角色扮演提示"的形式引导用户理解每个 OPC 角色（产品/市场/交付/文档）在干什么，产出为**结构化草稿**，由主理人审阅、修改、接受或退回。**它的目标是"帮用户理解角色"，不是"替用户干活"。**

## 5. 精简阶段模型（取代 v1.0 的 S0–S9 十阶段）

v1.0 的 S0–S9 是"贴近真实公司的十阶段门禁流水线"，过重且依赖真实交付。v2.0 收敛为主体一条主线的 **G0–G4 五步虚拟主线**：

| 阶段 | 核心问题 | 虚拟成果（结构化） | 门禁 |
|---|---|---|---|
| G0 想法 | 我为什么想解决这个问题？ | 想法卡：问题、目标用户、价值假设 | 信息完整即可保存 |
| G1 目标与方案 | 我打算交付什么、用什么方案？ | 目标卡 + 方案卡 + 不做清单 | 主理人确认 |
| G2 执行（产出） | 我做出了什么虚拟成果？ | 虚拟产出（文档/设计/数据/脚本/演示）+ 任务与版次 | 产出元数据完整 + 可审阅 |
| G3 验证与反馈 | 这个想法/成果行不行？ | 反馈记录、验证假设、复盘要点 | 表单完整（模拟反馈） |
| G4 复盘与闭环 | 继续、转向、暂停还是终止？ | 复盘报告 + 成果包 + 结项/转向/终止记录 | 评审或主理人确认 |

- **每步都产出一个"可审阅、可回退、可存档"的结构化虚拟记录**，不是必须真实上线的产品。
- 领域模板（软件/内容/校园服务/科研实验/公益等）只做引导，不锁死方向。
- L1 纯学习不建项目；**进入 L2** 即创建 G0 虚拟项目；L2 跑通即覆盖 G0–G3；**L3** 加入 G4 与结项状态机、里程碑门禁、风险分级、成果仓库与展示。

### 5.1 项目生命周期状态（沿用 v1.0 状态机，收敛）
`draft → idea_received → running → validating → closed`
异常状态：`paused_result`、`pivoted`、`terminated`、`archived`、`risk_frozen`（保留，用于复盘教学）。
项目允许失败，`terminated` 必须提交原因与复盘。

## 6. 本期实现范围（基于当前环境）

### 6.1 保留/沿用 v1.0 已实现且当前环境可跑的骨架
- 学院准入三层边界 + `/vopc` 主菜单与路由（fail-closed）
- 项目/成员关系/任务/产出/决策/里程碑的基础数据模型与 API
- 里程碑安全门禁（active/intended_stage/成果版本去重/数量上限）、结项状态机（close/pause/pivot/terminate/archive，CAS+审计）、风险分级与治理闭环、R3 专项通道
- 私有文件受控上传 + 鉴权下载（本地/可配置存储，不做云对象存储）
- 审计日志

### 6.2 v2.0 新增/调整（教学导向）
- L1 概念页与"OPC 核心流程图"交互
- L2 虚拟向导（模板化引导）与"精简主线 G0–G4"项目向导
- 各阶段"结构性虚拟产出"表单与"可回退/可重开"机制
- L3 默认开放：结项复盘模板、成果包导出（简化）
- 数据模型与代码分层预留 L4 扩展位（不实现功能）

### 6.3 本期明确不做（降为 L4 预留 / 从 P0 移除）
- 真实模型 API 执行、项目上下文隔离（真 AI）
- 云对象存储 + 病毒扫描 + 签名 URL（文件走本地/可配置受控存储即可）
- 真实支付、合同、税务、结算
- 真实 MySQL/Turso 生产同构升级与并发、多端/WebView、P95 压测、备份恢复演练
- 全量 Flutter lint 清零（仅保证 vOPC 相关 build/analyze 通过）

> 这些在 v1.0 是"缺环境无法实现"的 P0 阻断项；在 v2.0 被**明确定位为 L4 远期预留，不进入本期验收口径**，从而解除 NO-GO 阻塞。

## 8. 核心功能需求（v2.0 收敛清单）

- **VOPC-F-101 L1 入门学习**：OPC 核心知识 + 核心流程图 + 自测；无需建项目。验收：任一授权用户可进入并在 5 分钟内理解 OPC 核心思想（以流程/测问答对为准）。
- **VOPC-F-102 虚拟项目创建**：从概念层或空白发起练习项目，向导补全 G0 想法卡；可存草稿。验收：任一登录用户 10 分钟内完成草稿。
- **VOPC-F-103 精简主线走通**：G0–G3 逐步填表产出虚拟成果，每一步可保存、回退、重开。
- **VOPC-F-104 虚拟向导**：每步基于项目类型给出模板/清单/角色扮演提示，产出结构化草稿，主理人审阅/修改/接受/退回（记录版次与修改率，供教学统计）。
- **VOPC-F-105 任务与协作**：任务（负责可为真人/向导）、议论、@、通知（复用蔚小芯通知）。
- **VOPC-F-106 决策记录**：关键决策背景/选项/建议/理由/结果（沿用）。
- **VOPC-F-107 里程碑门禁**：G 阶段里程碑提交 + 指定评审 + pass/return（沿用 v1.0 安全实现）。
- **VOPC-F-108 结项与复盘**：close / pause / pivot / terminate / archive 状态机 + 复盘模板 + 成果包导出（沿用 v1.0 状态机，教学口径）。
- **VOPC-F-109 风险分级**：R0–R3 分级与治理/专项通道（沿用 v1.0；R2/R3 不批不可推进里程碑）。
- **VOPC-F-110 虚拟成果仓库**：结构化产出 + 受控文件上传/下载 + 版本与可见范围（本地/可配置存储版）。
- **VOPC-F-111 成果展示**：经授权进入学院内成果展厅（沿用可见性边界）。
- **VOPC-F-112 辅导点评**：导师/评审在项目、任务、产出、里程碑层点评（v2.0 定位为"辅导"而非"真实经营审计"）。

## 12. 分期（v2.0）

### P0（本期 · 教学闭环，与当前环境匹配）
- L1 概念层 + `/vopc` 入门
- L2 精简主线 G0–G4 + 虚拟向导 + 虚拟项目/任务/产出/决策
- L3 结项状态机、里程碑门禁、风险分级、成果仓库/展示/复盘
- 学院准入、可见性、审计、本地受控文件

### P1（后续 · 在教学闭环上增强）
- 领域模板扩充、伙伴/协作者匹配、导师库、成果展厅运营
- 更多"虚拟向导"角色与更丰富的引导模板

### P2（远期 · L4 现实延伸预留）
- 仅在架构与数据层预留；待真实 AI/对象存储/生产同构环境具备后再评估实现真实执行、云存储、多端、真实经营。**本期一律不实现。**

## 13. 验收口径（v2.0）

### 13.1 功能验收（以"能理解 OPC"为准）
1. 任一授权用户可进入 vOPC 并完成 L1 入门（理解核心思想）；
2. 可创建虚拟练习项目并走通 G0–G3 主线，产出结构化虚拟记录；
3. 虚拟向导可给出模板化引导，产出可审阅/修改/接受/退回并保留版次；
4. L3 可完成里程碑评审、结项/暂停/转向/终止/复盘与成果包导出；
5. 风险分级 R2/R3 门禁与专项通道生效；
6. 项目默认私有，未经授权不可进入学院展示；
7. 关键操作与向导调用可审计。

### 13.2 权限验收
沿用 v1.0（非成员不可读私有项目；成员不可越权改角色/可见性；导师只可访问授权项目；学院外一律拒绝）。

### 13.3 性能与可靠性（按当前环境）
- 常规列表/工作台请求 P95 < 2 秒（不含外部调用，本版无外部模型调用）；
- 向导任务支持失败重试与明确失败状态；单任务失败不阻塞项目；
- 文件上传/鉴权/审计失败不得虚假成功。

### 13.4 安全验收
沿用 v1.0（R2/R3 拦截/审核；私有文件鉴权；敏感信息提示；展示需申请审核；关键数据备份/归档/恢复策略——备份恢复演练属 L4，归档/恢复策略为本期）。

## 14. 试点（v2.0）

首轮试点改为"OPC 核心思想掌握度"验证，小规模多角色即可：
- 本科各年级 + 研究生 + 教师/辅导员/管理员各若干，覆盖 15–25 个练习项目（软件、内容、校园服务、科研实验、公益均可）。
- 试点 3–4 周，重点验证：
  1. 不同角色都能走通 L1–L3 并理解 OPC 核心思想；
  2. 非软件项目也能使用虚拟向导与精简流程；
  3. 用户会真正审阅/修改/退回向导产出，而不是只点接受；
  4. 项目能产生可展示的虚拟成果或有证据的失败复盘；
  5. 平台运营与审核工作量可控。

成功指标不以"成立多少公司/上线多少产品"衡量，而以"用户能否讲清 OPC 核心思想并独立走通一条虚拟主线"衡量。

## 16. 最终产品定义（v2.0）

> **vOPC 是蔚小芯面向计算机学院授权用户开放的虚拟 OPC（一人公司）教学模块。用户通过四个复杂度层级——概念层（认识 OPC 核心思想）、流程层（跑通需求→成果→反馈的主线）、闭环层（走完复盘/结项/转向/终上的完整生命周期）、现实预留层（远期真实延伸，本期不做）——在"虚拟向导"的模板化引导下，以主理人身份把一个想法推进为可审阅、可复盘、可展示的虚拟成果，从而掌握 OPC 的核心思想与流程。外院、校外与游客不提供访问权限。vOPC 不追求真实公司经营，过度真实的公司流程在当前无运行环境，一律作为远期预留，不拖累核心教学闭环。**
