# 蔚小芯智能体

> **项目定位**: 信息学院智慧校园 AI 学工助手（蔚小芯）  
> **服务对象**: 全院师生、辅导员、学院管理者、全体学生  
> **核心目标**: 实用性强、可落地、解决真实痛点  
> **收费策略**: 不收费  
> **技术栈**: Flutter (跨端前端) + Golang (后端) + Context Engine（上下文引擎/知识增强）+ 智谱清言API + DeepSeek API + 讯飞星火语音API
> **核心约束**: 知识增强为项目必选能力，采用 **Context Engine（结构化数据 + 全文检索/BM25/FTS + 上下文拼装）** 为主链路；向量检索与 Agentic RAG 为**可插拔组件**（复杂问题按需启用），长文档按需采用 Long Context。 不使用本地大模型部署；不使用Docker、容器化、集群部署；不依赖Coze等第三方智能体平台。**多智能体管理中心、策略与元数据自研**；编排与协同运行时采用可自部署的开源框架（Eino）+ 自研业务封装，关键链路可选用 Temporal 增强可靠性（详见 4.3.1）。
> **项目周期**: 14 天（2026年5月1日 - 2026年5月14日）

## 1. 项目背景与目标

### 1.1 项目背景

信息学院近年来大力推进智慧校园建设，已建成完善的学工信息化体系：

- **新学工系统**: 35 个模块，覆盖奖助学金、请假、心理咨询等业务
- **一表通系统**: 数据共享，避免重复填报
- **掌上蔚园**: 移动端统一入口
- **综合服务门户**: 统一身份认证

**建设与对接范围说明**：本智能体由**信息学院**牵头建设与试点，服务对象以本院师生为主；学工、一表通、统一门户等为**校级既有系统**，本期以**经授权后的只读/代理访问**为主（写操作与全量数据范围以校方批复为准），避免与校级建设主体表述混淆。

**命名与定位确认**：经与刘书记、何书记座谈确认，智能体正式命名为"**蔚小芯**"，聚焦入学、在校、毕业三个阶段的教育服务。

### 3.3 Context Engine（上下文引擎）知识增强方案（主路线）

为降低维护成本、提升可控性与可溯源能力，蔚小芯采用“**结构化优先 + 全文检索为主 + 向量与 Agentic 按需**”的上下文引擎（Context Engine）作为主路线：

- **结构化优先（强确定性）**：流程节点、材料清单、入口链接、时间地点、适用对象等写入结构化库（SQLite），优先以结构化结果回答。
- **全文检索主召回（低成本/高可控）**：对政策/通知/指南/FAQ 的正文启用 FTS/BM25 检索，返回 Top-K 片段用于生成与引用。
- **上下文拼装（可解释）**：将“结构化结果 + 检索片段 + 版本/适用范围”拼装为上下文，交由模型生成最终回答。
- **向量检索（可插拔增强）**：仅在“同义问法多、长尾强、关键词不稳定”的知识域启用（例如 FAQ/政策原文），作为补充召回而非唯一召回。
- **Agentic RAG（按需触发）**：对“对比/归纳/跨文档多跳推理”问题，启用多轮检索-推理循环；普通问题不进入该链路以控制延迟与成本。
- **Long Context（小范围全文）**：对少量高价值长文（如毕业离校手册）按需加载关键章节全文，减少切分带来的断章问题。
- **来源可追溯（硬约束）**：每条回答必须附带 `sources`（文档标题/链接/版本号/段落），未命中或低置信则触发兜底回复，不允许无依据生成。
- **权限隔离与治理**：按学院/角色过滤可见内容；学生会采集整理，学院审核发布；过期内容降权或下线，保留历史版本以便追溯。

分期实施建议：

1. **P0（必须）**：入学教育 + 离校教育知识域完成结构化库与全文检索链路上线（可选启用少量向量增强）
2. **P1（扩展）**：在校教育重点活动与学籍学情知识域接入；引入可选重排/评估
3. **P2（优化）**：Agentic 触发策略、质量看板、自动更新与缓存路由完善

#### 3.3.1 触发策略（路由规则表）

将“查什么、怎么查、查几次”从模型里剥离为可配置策略，保证**低延迟主链路**与**复杂问题增强链路**同时成立：


| 典型问题                | 首选通道                  | 触发条件（进入）                                        | 输出形态要求                                | 备注             |
| ------------------- | --------------------- | ----------------------------------------------- | ------------------------------------- | -------------- |
| 办事流程/材料清单/入口链接/时间地点 | 结构化库（SQLite）          | 命中流程类意图（leave/grant/party/volunteer/etc）        | 步骤清单 + 入口链接 + 材料清单 + 截止时间 + `sources` | 最低延迟、最强确定性     |
| 政策条款解释/条件判断/适用对象    | FTS/BM25（全文检索）        | policy/eligibility/condition 意图                 | 引用卡必须包含：文档标题/段落/版本/生效时间               | 以“引用可追溯”为第一目标  |
| FAQ 长尾同义问法（关键词不稳定）  | 向量检索（可选增强）            | FTS 命中不足或召回置信低；或同义问识别                           | 仍需 `sources`；优先给可执行结论                 | 向量只做补召回，不独立出答案 |
| 跨文档对比/归纳/多跳推理       | Agentic RAG（按需）       | 检测到 compare/summarize/multi-hop；或用户追问“依据在哪/为什么” | 多引用合并 + 分点结论 + 风险提示                   | 限制最大轮次与超时，避免拖慢 |
| 高价值长文（毕业离校手册/制度汇编）  | Long Context（按需小范围全文） | 命中“手册类”文档，且需要跨章节逻辑                              | 引用章节/页码/版本；可导出 PDF                    | 只对少量文档启用，控成本   |
| 未命中/低置信/权限不足        | 兜底策略                  | 无有效检索结果；或被权限过滤；或冲突条款                            | 明确“不确定”+ 指向官方渠道/辅导员                   | 不允许编造政策细节      |


#### 3.3.2 检索与上下文拼装参数（建议默认值）

- **FTS/BM25**：Top-K=5（初始），每条片段 200-400 字；按 `ownerScope/roleScope` 过滤后再排序
- **向量检索（可选）**：Top-K=8（补召回），与 FTS 结果去重合并后再重排（可选）
- **重排（可选）**：对合并候选 Top-N=10 做轻量重排；P0 可先不启用
- **上下文预算**：结构化结果优先写入；检索片段按“新鲜度（版本）+ 适用范围 + 相似度”排序截断
- **缓存**：对高频问法缓存“检索结果与引用片段”，不缓存最终自然语言（避免过期传播）

#### 3.3.3 引用与合规输出规范（必须）

- 每条政策/条件类回答必须返回 `sources[]`，至少 1 条；每条 source 含：标题、链接、版本号、生效时间、段落摘要
- 如果 sources 为空或置信不足：禁止给出确定条款与金额/时间等关键数字；必须输出兜底提示
- 对不同角色输出不同粒度：学生版“结论+步骤”；辅导员/学院版额外包含“依据+例外情况+风险提示”

#### 3.3.4 知识切分与元数据规范（工程落地）

为保证检索稳定、权限正确、引用可追溯，所有知识资源统一遵循以下入库规范（与 6.8 对接字段一致）。

**通用元数据（必填）**：

- `resourceId`：全局唯一（建议 `type_scope_date_seq`）
- `resourceType`：Policy/Process/FAQ/Activity
- `ownerScope`：school/college/class（学院内可扩展 `ownerId`）
- `roleScope`：sys_admin/school_admin/college_admin/counselor/student_union/student
- `version`：建议 `YYYYMMDD-vN` 或与原系统版本一致
- `status`：draft/pending/published/retired
- `title`：标题
- `sourceLink`：原文链接或系统内引用
- `sourceVersion`：原文版本/发布日期
- `effectiveAt` / `expiredAt`：生效/失效时间（无则空）
- `tags`：主题标签（奖助/请假/党团/就业…）
- `updatedBy` / `updatedAt`：更新人/时间

**内容字段（必填）**：

- `summary`：200-400 字摘要（用于快速回答与导出）
- `content`：可检索正文（清洗后的正文；用于 FTS/BM25）

**切分策略（chunking）**（用于“全文检索片段 + 可选向量增强”）：

- **Policy**：按“章/条/款”切分；每块建议 200-400 字；保留条款编号（如“第二章 第三条”）用于引用
- **Process**：按“步骤节点”切分；每块包含：步骤名、材料、入口、时限、注意事项；优先同步到结构化库
- **FAQ**：按“Q/A 对”切分；同义问放入 `aliases[]`（可选）；标准答必须绑定至少 1 条 source
- **Activity**：按“活动要素”切分；包含时间地点/报名入口/负责人/模板/海报；到期自动标记 `retired`

**权限与脱敏规则（必须）**：

- 检索前先过滤：`ownerScope/roleScope/status=published`，再做排序
- 涉及个人敏感信息（学号/手机号/身份证等）不得入库为可检索正文；必须走结构化字段并按角色脱敏展示

#### 3.3.5 质量指标与看板（验收与运营）

为保证“好用+可信+可控”，建议建立上下文引擎的最小质量看板（P0 即可落地统计，P1 起做可视化）。

**检索与引用类指标**：

- **引用覆盖率**：回答中 `sources` 非空的比例（目标：政策类=100%，流程类>=95%）
- **命中率**：用户问题在 Top-K 检索中命中正确文档的比例（抽检）
- **兜底率**：触发兜底回复比例（过高说明知识不足/检索差）
- **过期引用率**：引用到已 `retired` 或过期版本的比例（目标趋近 0）
- **权限拦截率**：因 roleScope/ownerScope 被过滤的请求比例（用于发现配置问题）

**体验与性能指标**：

- **首包时间（流式）P95**：首次返回文本/卡片的时间
- **整体时延 P95**：包含检索与模型调用（并单列第三方模型超时率）
- **点击转化**：步骤清单勾选/入口点击/导出/收藏/转发的转化率（衡量吸引力）

**内容治理指标（学生会运营）**：

- **新增条目数** / **审核通过率** / **平均审核时长**
- **错答修复周期**：从反馈到修复上线的时间
- **热点问题覆盖率**：Top100 高频问法中已覆盖的比例

**复盘机制**：

- 每周输出一次“热点问题 + 兜底原因 + 修复计划”报告（学生会运营组牵头，辅导员/学院管理员审核）

### 3.5 多模态回答与多格式导出（高吸引力设计）

为提升留存与传播效果，蔚小芯在“回答”层面采用 **结构化输出 + 多模态渲染 + 一键导出** 的统一设计。

#### 3.5.1 统一回答结构（AnswerCard 规范）

后端将模型输出标准化为可渲染的结构对象，前端按端能力（Web/APP/小程序）展示：

- **主回答卡**：一句话结论 + 3-5 条要点
- **步骤清单**：可勾选 checklist（材料、入口、截止时间、办理地点）
- **来源引用**：文档标题/链接/版本号/适用对象（知识增强必须返回）
- **风险提示**：不确定项、需人工确认项、以最新通知为准
- **下一步追问**：3-5 个建议追问按钮（提升会话深度）
- **可执行动作**：收藏、转发、生成通知稿/材料模板、导出为 PDF/Word/长图等

#### 3.5.2 多模态回答形态（按分期落地）


| 分期  | 形态              | 说明                      |
| --- | --------------- | ----------------------- |
| P0  | 文本 + 步骤清单 + 引用卡 | 主打“好用+可信”，适配入学/离校 MVP   |
| P1  | 语音播报（TTS）+ 高亮要点 | 支持“边听边看”，适合移动端          |
| P1  | 海报式长图           | 活动通知/流程指引一键生成，利于传播      |
| P2  | 材料模板生成          | 申请材料要点/通知稿/推文草案（带来源与水印） |


#### 3.5.3 多格式导出（回答即成果）

导出目标是让用户把回答“带走/传播/复用”，并且可审计、可追溯：

- **PDF**：正式版（含标题、时间、版本号、水印、来源脚注）
- **Word(.docx)**：可编辑材料/通知稿
- **Markdown**：便于学生会与学院维护沉淀
- **Excel(.xlsx)**：清单/统计/名单模板
- **PNG 长图**：分享传播（群聊/朋友圈/公众号）
- **ICS 日历**：报名截止/宣讲会一键加入日程
- **JSON**：与“蔚园智答”等系统对接

#### 3.5.4 导出与审计要求

- 所有导出必须记录：导出人、角色、时间、导出格式、是否包含敏感字段、traceId
- 导出内容必须带：版本号、来源引用（sources）、生成时间、适用范围
- 对“学院/学校级导出”启用水印与二次确认（防止误传与过期传播）

### 4.3 多智能体核心能力（自研）

```
1. 智能体全生命周期管理：注册、配置、分类、启停、权限绑定、元数据管理
2. 智能体流程编排：任务链路定义、执行逻辑配置、分支规则、多智能体协作流程设计
3. 任务调度引擎：并发调度、优先级调度、负载均衡、超时控制、异常熔断、失败重试
4. 协同交互能力：上下文隔离与共享、任务自动分发、跨智能体联动、结果汇总与整合
5. 扩展能力：配置化新增智能体，无需改动底层架构，支持动态更新调度策略
```

上述第 1、5 条中的**管理控制台、策略与租户级配置**仍采用**自研**；第 2～4 条的**编排运行时**采用**开源框架 + 自研业务封装**，避免从零实现图编排与流式协同，与「不依赖 Coze 等第三方智能体平台」不冲突（使用可自部署的开源库）。

#### 4.3.1 推荐技术组合：Golang 一队到底


| 层级          | 选型                             | 职责                                                                        |
| ----------- | ------------------------------ | ------------------------------------------------------------------------- |
| 网关与权限       | **Gin + JWT + RBAC**           | 对外 API、认证鉴权、租户/角色范围、限流与审计入口                                               |
| 多智能体编排      | **Eino**（CloudWeGo，Apache-2.0） | 主编排：Graph/Workflow、多 Agent 协同、上下文与工具调用、中断/恢复、可观测钩子；对接智谱/DeepSeek HTTP API |
| 关键链路可靠性（可选） | **Temporal**（Go SDK）           | 对长事务、跨多步调用链路：幂等、超时、重试、熔断与可恢复工作流；适用于学工/一表通串联、多智能体长链路与试点高可靠场景               |
| 自研补足        | 多智能体管理中心、注册审批、配额与元数据           | 与 Eino/Temporal 通过内部接口衔接，不绑定外部 SaaS                                       |


**集成方式简述**：客户端与外部系统先经 **Gin** 完成鉴权与路由；业务聚合层调用 **Eino** 执行对话与多智能体编排（含 SSE 流式）；对标注为「关键路径」的流程（如批量政策同步、对接失败需补偿）可下沉为 **Temporal Workflow**，Activity 内调用模型或 HTTP 代理，实现与「7×24 + 可恢复」一致的服务质量目标。

**开源参考**：Eino —— [https://github.com/cloudwego/eino](https://github.com/cloudwego/eino) ；Temporal —— [https://github.com/temporalio/temporal](https://github.com/temporalio/temporal) （部署与运维由项目侧按学院环境选择，仍符合「无 Docker 强制」前提下可用二进制/原生方式部署）。

#### 6.5.2 重点结论：Flutter + Dart 能否满足需求？

**结论：能满足当前需求，且是本项目的合理主选方案。**

理由如下：

- **多端覆盖能力匹配**：同一套代码可覆盖 Android、iOS、Web，满足“门户 Web + 独立移动端”主场景。
- **业务复杂度适配**：你当前主要是表单、列表、消息流、权限界面、SSE 问答流，这些都是 Flutter 成熟能力。
- **语音与网络能力可用**：Flutter 生态可满足录音、播放、HTTP/SSE、本地缓存、状态管理等需求。
- **开发效率高于多端原生并行**：14 天 MVP 周期下，Flutter 更容易保证“先可用再优化”。

#### 6.5.3 边界与建议（避免踩坑）

- **微信小程序**：Flutter 不能直接原生产出标准微信小程序，建议小程序端单独实现轻量版（与后端复用接口）。
- **鸿蒙**：若需严格原生体验或特性，建议先以 Android 兼容方案落地，再评估 HarmonyOS 专项适配成本。
- **快应用生态差异**：不同校园平台标准不一，建议将“快应用”作为 P1，不阻塞 P0 MVP 验收。
- **实施顺序建议**：P0 优先 Web + Android；P1 补 iOS 与微信入口；P2 再做快应用与深度鸿蒙优化。

### 6.7 数据体系说明

系统数据由三类构成：

1. **校内业务数据**：学校学工系统、一表通等对接数据（经授权访问）
2. **自建核心数据**：知识库与问答库（政策条目、流程模板、FAQ）
3. **运行沉淀数据**：系统运行产生的问答日志、热点问题、使用行为与反馈数据

### 6.8 知识库导入导出与”蔚园智答”对接（重点）

目标：让知识库**可治理、可迁移、可同步**，并支持将本系统知识导入到”蔚园智答”既有应用。

**调研结论（信息中心白老师）**：蔚园智答平台已在运行，后续方向为扩充知识库与更新平台能力。蔚小芯作为学院侧知识生产与治理的入口，通过下述同步协议向蔚园智答输出结构化知识，实现”学院采集治理—平台统一服务”的协作模式。

#### 6.8.1 知识库资源模型（四类资源）

1. **Policy（政策）**：政策原文/链接/摘要要点/生效日期/适用范围/版本
2. **Process（流程）**：流程节点、材料清单、入口链接、时限、常见问题
3. **FAQ（问答）**：标准问、同义问、标准答、引用来源
4. **Activity（活动/通知）**：时间地点、报名入口、负责人、海报、模板

每条资源必须包含：`resourceId`、`resourceType`、`ownerScope`、`roleScope`、`version`、`status`、`sourceLink`、`tags`、`updatedBy`、`updatedAt`。

#### 6.8.2 导入方式（学生会可参与）

- **批量导入**：支持 Excel/Word/PDF/Markdown/网页链接
- **向导式导入**：选择资源类型 -> 填元数据 -> 上传/抓取 -> 自动切分 -> 预览召回 -> 提交审核
- **增量更新**：同一资源新版本导入后，自动更新索引并保留历史版本（可回滚）

#### 6.8.3 导出方式（系统对接友好）

- **全量导出**：按学院/类型/时间范围导出（用于冷启动或迁移）
- **增量导出（推荐）**：按 `updatedAt` 或 `version` 导出变更集（用于日常同步）
- **导出格式**：zip 包或 API 流式下载；包含 manifest 与资源清单

#### 6.8.4 与“蔚园智答”同步模式

优先支持两种模式，适配对方能力差异：

- **模式 A（推荐，API 同步）**：蔚小芯提供 Export API；蔚园智答提供 Import API（或拉取接口）。按增量定时同步，带版本与下线状态。
- **模式 B（兜底，文件包导入）**：蔚小芯导出标准包，蔚园智答管理员手工上传导入。

同步必须满足：版本去重（`resourceId + version`）、冲突策略（高版本覆盖低版本）、权限映射（ownerScope/roleScope 一并同步）。

#### 6.8.7 标准导出包结构（manifest + 资源清单）

为兼容“API 同步”和“文件包导入”两种模式，蔚小芯导出包采用固定结构：

- `manifest.json`（包元信息、校验、游标）
- `resources.ndjson`（每行一条资源 JSON，便于流式导入）
- `attachments/`（可选：原始文件/海报/模板等附件）

`manifest.json` 示例（最小可用）：

```json
{
  "packageId": "pkg_20260430_0001",
  "producer": "weixiaoxin",
  "schemaVersion": "1.0",
  "exportType": "full|delta",
  "ownerScope": "school|college|class",
  "ownerId": "string",
  "sinceCursor": "string",
  "untilCursor": "string",
  "generatedAt": "2026-04-30T21:40:00+08:00",
  "resourceCount": 123,
  "hashAlg": "sha256",
  "resourcesSha256": "hex",
  "attachmentsSha256": "hex",
  "signAlg": "hmac-sha256",
  "signature": "hex"
}
```

说明：

- `cursor` 用于增量同步定位（见 6.8.8）
- `resources.ndjson` 的整体哈希用于防篡改与幂等校验

#### 6.8.8 增量同步协议（cursor/幂等/冲突）

**推荐协议**：以 `cursor`（单调递增）作为增量同步基准，避免依赖时钟不一致。

- **cursor 生成**：可采用数据库自增序列或 `(updatedAt, resourceId)` 的可排序组合；要求单调递增。
- **幂等键**：`(resourceId, version, status)` 作为幂等落库键；重复导入必须无副作用。
- **冲突策略**：
  - 同 `resourceId`：版本号更高覆盖更低；同版本重复忽略
  - `status=retired` 必须传播（用于下线/过期）
  - `ownerScope/roleScope` 变化视作新版本（提升可追溯性）

**API 同步建议**（模式 A）：

- `GET /kb/export?ownerScope=college&ownerId=xxx&sinceCursor=...&limit=...`
  - 返回 `manifest + resources.ndjson`（或分块流）
- `POST /kb/import`
  - 支持上传导出包或 ndjson 流
  - 返回 `appliedCount/ignoredCount/conflictCount/untilCursor`

#### 6.8.9 鉴权与校验（对接安全底线）

为避免知识包被篡改或越权导入，建议对接层采用以下底线：

- **传输层**：HTTPS
- **调用鉴权**：`Authorization: Bearer <token>`（或双方约定的服务间 token）
- **包签名**：`signature = HMAC_SHA256(secret, resourcesSha256 + attachmentsSha256 + untilCursor)`
- **完整性校验**：导入前校验 `resourcesSha256/attachmentsSha256`；不通过则拒绝导入
- **审计记录**：记录导出方、导入方、时间、ownerScope、resourceCount、cursor 范围、traceId
- **权限校验**：导入时必须校验 `ownerScope/ownerId/roleScope` 是否在目标系统允许范围内

### 9.2 安全与审计基线

- 认证：统一身份认证 + JWT，Token 过期时间 2 小时，支持刷新
- 授权：RBAC **至少 6 级角色**（见 6.6），最小权限原则；支持学校/学院/辅导员/学生会等多级授权与审计
- 脱敏：学号、手机号、身份证等字段按规则脱敏展示
- 审计：记录操作人、时间、接口、结果码、耗时、追踪ID
- 告警：连续5分钟错误率>2% 或 P95>3秒触发告警
- 保留：关键审计日志至少保留 180 天

### 9.2.1 数据隐私与合规要求

- **隐私影响评估（PIA）**：上线前须完成隐私影响评估草案，覆盖数据收集范围、使用目的、存储期限、共享方与法律依据
- **用户授权**：首次使用需用户确认隐私政策与数据使用协议；情感分析功能需单独授权弹窗
- **数据最小化**：仅采集业务必需字段；会话记录保留期限不超过 1 学年，到期自动清理或匿名化
- **个人信息分类分级**：按《个人信息保护法》要求，对学号、手机号、身份证号等敏感信息标注分级（一般/敏感），并落实相应保护措施
- **跨境限制**：所有数据存储于境内服务器；LLM API 须选用境内节点或确认数据不出境

### 9.2.2 LLM API 数据安全措施

- **请求脱敏**：发送至第三方 LLM API 的 prompt 中，不得包含学号、姓名、身份证号、手机号等可识别个人信息；需在网关层做自动脱敏替换
- **传输加密**：所有 LLM API 调用强制 HTTPS/TLS 1.2+
- **响应审计**：记录每次 LLM 调用的 traceId、token 消耗、是否触发内容安全过滤，但不持久化完整 prompt/response 原文（仅保留摘要与 hash）
- **内容安全过滤**：对模型返回内容做关键词与规则过滤，拦截不当内容后返回兜底回复
- **供应商合规**：选用的 LLM API 供应商须提供数据处理协议（DPA），明确不使用客户数据进行模型训练

### A.5 错误码细分（知识同步与导出）

在 `0=成功,4xxx=客户端错误,5xxx=服务端错误` 的总原则下，建议统一以下细分错误码：


| 错误码  | 场景        | 说明                                        | 处理建议           |
| ---- | --------- | ----------------------------------------- | -------------- |
| 4001 | 参数缺失      | 必填参数缺失（如 `ownerScope`、`exportType`）       | 修正参数后重试        |
| 4002 | 参数非法      | 枚举值/格式不合法（如 `exportType` 非 `full          | delta`）        |
| 4003 | 鉴权失败      | Token 无效/过期/无权限                           | 重新登录或刷新 Token  |
| 4004 | 权限不足      | `ownerScope/roleScope` 超出调用方权限            | 降低范围或申请权限      |
| 4005 | cursor 非法 | `sinceCursor` 不存在、已过期或不在可用区间              | 改用全量或最新 cursor |
| 4006 | 包结构非法     | 缺少 `manifest.json` 或 `resources.ndjson`   | 按规范重打包         |
| 4007 | hash 校验失败 | `resourcesSha256`/`attachmentsSha256` 不匹配 | 重新导出并校验        |
| 4008 | 签名校验失败    | `signature` 验证失败（HMAC 不通过）                | 校对密钥与签名串       |
| 4009 | 幂等冲突      | 同 `resourceId+version+status` 重复导入        | 可忽略或走更新流程      |
| 4010 | 版本冲突      | 导入版本低于现网版本                                | 以高版本为准，检查数据源   |
| 4011 | 附件过大      | 文件大小超限或类型不支持                              | 分片上传或压缩附件      |
| 4290 | 频率超限      | 请求速率超限                                    | 指数退避重试         |
| 5001 | 导出失败      | 服务端生成包失败                                  | 查询 traceId 并重试 |
| 5002 | 导入失败      | 服务端入库异常                                   | 查询 traceId 并重试 |
| 5003 | 存储异常      | 数据库/对象存储不可用                               | 等待恢复后重试        |
| 5004 | 下游异常      | 学工/一表通等下游调用失败                             | 启用降级或延迟重试      |


### A.6 `/kb/export` 与 `/kb/import` 分页分块规范

为支持大规模知识同步、稳定重试与断点续传，建议采用如下协议：

#### A.6.1 导出分页（Export Pagination）

- 请求参数：
  - `limit`：单次导出资源条数（建议默认 `1000`，最大 `5000`）
  - `sinceCursor`：增量起点（delta 模式必填）
- 返回字段（建议）：
  - `nextCursor`：下一页游标，空表示已完成
  - `hasMore`：是否还有下一页
  - `exportBatchId`：本次导出批次标识（用于审计）

#### A.6.2 NDJSON 分块（Chunk Streaming）

- `resources.ndjson` 建议按行流式输出，便于低内存导入
- 推荐单块大小：`1MB ~ 4MB`（或 `500 ~ 2000` 行）
- 块级校验：可选 `chunkSha256[]`（提高断点续传可靠性）

#### A.6.3 导入分片与断点续传（Import Resume）

- 导入请求建议支持 `uploadId + chunkIndex + totalChunks`
- 导入状态查询接口（可选）：
  - `GET /api/v1/kb/import/status?uploadId=...`
  - 返回 `receivedChunks/appliedCount/lastCursor/errorChunks`
- 若分片中断，仅重传失败 `chunkIndex`，避免全包重传

#### A.6.4 重试与退避策略（Retry Policy）

- `5xx` 或 `4290`：采用指数退避（1s/2s/4s/8s，最多 5 次）
- `4007/4008`（hash/签名失败）：禁止盲目重试，需重新生成包
- `4009`（幂等冲突）：按“已处理”记录，不视为失败

#### A.6.5 一致性与完成判定

导入完成需同时满足：

1. `appliedCount + ignoredCount + conflictCount == receivedCount`
2. `untilCursor` 已推进且可被下一次增量读取
3. `resourcesSha256` 与服务端落库校验一致
4. 审计日志写入成功（含 `traceId`、调用方、scope、耗时）

| IT-302 | 分块上传中断恢复  | 上传到一半中断，仅重传失败 chunk                  | 导入完成且总计数正确，无重复写入                |
| IT-303 | 非法 cursor | 使用不存在/过期 cursor 导出                   | 返回 `4005`，并给出重置建议（全量或最近 cursor） |
