# 蔚小芯后端迁移方案：Vercel Serverless → 常驻云服务器

> 面向 5000 人校级规模。目标：稳定承载 LLM 长请求、恢复被 Turso 禁用的 FTS5 全文检索、把月度成本压到可预测区间。

## 一、结论先行（TL;DR）

| 项 | 现状（Vercel + Turso + CF） | 迁移后（常驻服务器 + 本地 SQLite + CF） |
|----|------|------|
| Go 后端 | Vercel Serverless，函数超时 ~10-60s，LLM 长回答易被掐断 | 常驻进程，长连接稳定，无超时 |
| 全文检索 | **FTS5 被跳过，BM25 检索降级**（见 `app.go:431`） | **本地 SQLite 恢复完整 FTS5/BM25** |
| 数据库 | Turso 云（HTTP 往返，每查询有网络延迟） | 本地 SQLite 文件（进程内，微秒级） |
| 月成本 | Vercel Pro $20 + Turso（超量后） | 云服务器 ¥60-200 |
| 可预测性 | 按调用量计费，活跃后失控 | 固定月租，可预测 |

**推荐路径**：一台 2-4 核常驻云服务器（国内厂商，数据合规）+ 本地 SQLite + Caddy 自动 TLS，前端继续留 Cloudflare Pages 免费版。代码几乎不用改——`main.go` 已是标准常驻服务。

## 二、为什么要迁（三个动因）

1. **Serverless 与 LLM 长请求根本错配**：大模型流式回答动辄 20-60s，Serverless 函数有执行时长上限，长对话会被中断；且按 GB-秒计费，5000 人活跃后成本不可控。
2. **FTS5 全文检索在 Turso 上被静默禁用**：`app.go` 的 `execSQL` 对 Turso 跳过所有 FTS5 语句，health 检查显示 `fts5: unavailable`。context_engine 的 BM25 召回是问答质量核心，现在跑在降级路径上。本地 SQLite（modernc 驱动）内置 FTS5，迁移即恢复。
3. **成本可预测**：固定月租替代按量计费，避免"用得越多越贵"。

## 三、关键前提：代码已就绪，无需重写

已具备的能力（无需新增代码）：

- **常驻 HTTP 服务**：`server/cmd/server/main.go` 已用 `http.Server` + `ListenAndServe`，含 `SIGINT/SIGTERM` 优雅关闭与审计日志 flush。
- **数据库自动识别**：`initDB` 按 DSN 前缀选驱动——`libsql://` → Turso，其他 → 本地 SQLite（WAL + busy_timeout + foreign_keys）。只需改 `SQLITE_PATH` 环境变量即可切回本地。
- **迁移自动执行**：启动时 `runMigrations` 从嵌入的 `migrations/*.sql` 增量执行；本地 SQLite 不再跳过 FTS5。
- **限流/配额已内置**：`GlobalIPRateLimiter`（100 req/min/IP）、`LoginIPRateLimiter`、`ChatUserRateLimiter`、`TokenStatsService`（日/月 chat 配额）。
- **PII 脱敏中间件**：`middleware.PIIMask()` 全局启用。

需要调整的只有 3 处 Serverless 让步（迁移后自动失效，无害）：
- `os.Getenv("VERCEL")` 分支：常驻环境下不进入，Temporal 可正常启用（若需要）。
- 上传目录 `/tmp/uploads` → 常驻服务器改为持久磁盘目录 `./data/uploads`（代码已是默认值，Vercel 才覆盖为 /tmp）。
- 无状态假设：常驻服务可安全使用本地文件缓存、内存态。

## 四、迁移步骤（按顺序，每步可回滚）

### 步骤 1：准备服务器
- 选型：国内云厂商轻量应用服务器（阿里云/腾讯云），**2 核 4G 起步**（5000 人日活建议 4 核 8G）。
- 系统：Ubuntu 22.04 LTS。
- 开放端口：`443`（HTTPS）、`22`（SSH，限来源 IP）。**不要**直接暴露 Go 的 `8080`。

### 步骤 2：数据迁移 Turso → 本地 SQLite
项目已有 `server/cmd/sync-db`（反向同步工具）。迁移时：
1. 从 Turso 导出全量数据（`turso db dump` 或 `sync-db` 反向）。
2. 在服务器生成本地 `wxx.db`，导入数据。
3. **首次启动让 `runMigrations` 补齐 FTS5 表与触发器**（Turso 上从未建过），随后回填 `kb_fts` 索引。
4. 校验：`/health` 应显示 `fts5: ok`（迁移前是 `unavailable`）。

### 步骤 3：构建与部署 Go 二进制
```bash
# 本地或服务器上交叉编译（注意 FTS5 需 CGO-free 的 modernc 驱动，已内置）
cd server && go build -tags fts5 -o /opt/wxx/wxx-server ./cmd/server
```
配置环境变量（`/etc/wxx/env` 或 systemd 的 `EnvironmentFile`）：
```
APP_MODE=release
APP_PORT=8080
SQLITE_PATH=/opt/wxx/data/wxx.db          # 关键：不带 libsql:// 前缀 = 走本地
JWT_SECRET=<与 CF Functions 一致的强密钥>
DEEPSEEK_API_KEY=<...>                     # 或 ZHIPU_API_KEY
CORS_ALLOWED_ORIGINS=https://wxx-agent.pages.dev
DAILY_CHAT_QUOTA_PER_USER=50               # LLM 成本闸门，见第六节
MONTHLY_CHAT_QUOTA_PER_USER=800
```

### 步骤 4：systemd 托管（进程常驻 + 自启 + 崩溃重启）
```ini
# /etc/systemd/system/wxx.service
[Unit]
Description=WXX Go Backend
After=network.target

[Service]
Type=simple
EnvironmentFile=/etc/wxx/env
ExecStart=/opt/wxx/wxx-server
WorkingDirectory=/opt/wxx
Restart=always
RestartSec=3
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
```
```bash
systemctl enable --now wxx && systemctl status wxx
```

### 步骤 5：Caddy 反向代理 + 自动 HTTPS
```
# /etc/caddy/Caddyfile —— 一行搞定 Let's Encrypt 证书自动签发/续期
api.pydaydayup.xyz {
    reverse_proxy localhost:8080
    request_body {
        max_size 60MB      # 匹配文档上传 50MB 上限
    }
}
```

### 步骤 6：切流量（CF Functions 指向新后端）
唯一要改的前端配置：把 Cloudflare Pages 的加密环境变量 `GO_BACKEND_URL` 从 Vercel 地址改为 `https://api.pydaydayup.xyz`。
```bash
npx wrangler@4 pages secret put GO_BACKEND_URL --project-name wxx-agent
# 输入：https://api.pydaydayup.xyz
```
CF Functions 只做认证代理（见 `functions/api/[[route]].js`），改指向后即时生效，**前端无需重新构建/发版**。

### 回滚
任何一步异常，把 `GO_BACKEND_URL` 改回 Vercel 地址即可秒级回退（Vercel 部署保留不删）。数据双写期内 Turso 仍是可用副本。

## 五、成本估算（5000 人规模）

价格为 2026 年初市场行情，**以云厂商实时报价为准**。

| 项目 | 方案 | 月成本（约） |
|------|------|-------------|
| 云服务器 | 阿里云/腾讯云轻量 4 核 8G 10Mbps | ¥150–220 |
| 前端托管 | Cloudflare Pages 免费版 | ¥0 |
| CI/CD | GitHub Actions（仓库已公开=无限免费） | ¥0 |
| 数据库 | 本地 SQLite（随服务器磁盘） | ¥0 |
| 域名 | 已有 pydaydayup.xyz | — |
| HTTPS 证书 | Caddy + Let's Encrypt 自动 | ¥0 |
| **基础设施小计** | | **¥150–220/月** |
| **大模型 API** | 见下节，取决于用量 | **¥数百–数千/月** |

**关键结论**：基础设施每月约 ¥150–220 是可控固定成本；真正的变量是大模型 API 调用费，必须靠配额和缓存压住。

## 六、大模型成本控制（真正的成本大头）

5000 人若不加限制，LLM 费用会失控。项目**已内置**多道闸门，迁移后需正确配置并启用：

1. **每用户日/月配额**（`TokenStatsService`）：环境变量 `DAILY_CHAT_QUOTA_PER_USER` / `MONTHLY_CHAT_QUOTA_PER_USER`。建议日 30–50 次起步，观察后调整。
2. **FAQ 缓存复用**（`chat_service` RetireFAQ 机制）：相同问题命中已发布 FAQ 直接返回，不走 LLM。**迁回本地 SQLite 恢复 FTS5 后，知识命中率显著上升，LLM 调用量随之下降**——这是本次迁移省钱的隐藏收益。
3. **上下文裁剪**（`selectRelevantHistory`）：历史消息按相关性选取 Top-N 而非全量塞入，减少输入 token。
4. **模型分级**：`initApp` 已支持 DeepSeek 优先、智谱备选。DeepSeek 单价更低，适合作主力；复杂任务再切高价模型。
5. **限流兜底**：`ChatUserRateLimiter` 防单用户刷接口。

**估算方法**：月费 ≈ 活跃用户数 × 人均月对话次数 × 单次平均 token × 模型单价 ×（1 − FAQ 命中率）。
以 DeepSeek 为例，若 5000 人中 1500 日活、人均日 5 次、单次约 2K token、FAQ 命中率 40%，月成本量级约几百到一千余元。**FAQ 命中率每提升 10 个百分点，LLM 费用直接降约 10%**——所以知识库运营质量直接决定成本。

## 七、容量核算：4 核 8G 能否扛 5000 人？

- **并发模型**：5000 注册 ≠ 5000 并发。校园场景日活约 20–40%，峰值并发通常低于日活的 5%（即约 50–150 并发请求）。
- **瓶颈不在 Go**：Gin + SQLite（WAL 多读）轻松处理数百 QPS 的常规接口。真正的耗时在 LLM 上游 API 的响应（几秒级），而这是**等待 I/O**，Go 协程开销极低，可轻松挂起上千等待中的请求。
- **SQLite 写入**：WAL 模式支持多读单写，审计日志已是异步写入（`auditWg`）。5000 人规模写压力不大；若未来写入成瓶颈，再评估 PostgreSQL。
- **结论**：4 核 8G 足以支撑 5000 人（日活 1500 量级）。8 核 16G 可留足余量。

## 八、运维与可靠性

- **备份**：`sqlite3 wxx.db ".backup /backup/wxx-$(date +%F).db"` 每日 cron；异地留存至对象存储（OSS/R2）。
- **监控**：`/health` 已含 DB/FTS5/LLM 状态；接入 Uptime Kuma 或云监控做存活告警。
- **日志**：systemd journald 收集；`gin.Logger()` + `AuditLog` 已记录请求与操作审计。
- **升级**：`go build` 新二进制 → `systemctl restart wxx`（优雅关闭保证在途请求完成），秒级重启。
- **单点风险**：单服务器是单点。5000 人可接受；若要高可用，后续可加一台 + 负载均衡，但需先把 SQLite 换成 PostgreSQL/Turso（共享存储）。当前规模不必过早优化。

## 九、迁移收益总结

| 维度 | Vercel Serverless（现状） | 常驻服务器（迁移后） |
|------|--------------------------|---------------------|
| FTS5 全文检索 | ❌ 禁用（检索降级） | ✅ 恢复，BM25 生效 |
| LLM 长请求 | ⚠️ 受函数时长限制易断 | ✅ 无时长限制 |
| 成本可预测性 | ⚠️ 按调用量浮动 | ✅ 固定 ¥150–220/月 |
| 数据合规 | 数据出境风险 | ✅ 数据留境内 |
| 冷启动 | ⚠️ 有冷启动延迟 | ✅ 常驻无冷启动 |
| 运维复杂度 | ✅ 免运维 | ⚠️ 需基础运维（systemd/备份） |

**净评价**：对 5000 人的校级问答系统，常驻服务器在检索质量、LLM 稳定性、成本可控、数据合规四个维度全面占优，代价是引入基础运维——这对一个正式运行的系统是合理且必要的投入。

## 十、腾讯云选型（结合未来微信小程序需求）

选腾讯云的额外理由：小程序是微信生态，后端放腾讯云在**同一云商内网**，配合微信支付、腾讯云短信、COS 对象存储等生态，链路更短、合规文档一套齐全。

### 10.1 产品选型

| 用途 | 腾讯云产品 | 建议规格 | 月成本（约） |
|------|-----------|---------|-------------|
| Go 后端主机 | 轻量应用服务器 Lighthouse | 4 核 8G 8Mbps | ¥110–180 |
| （高活跃备选） | 云服务器 CVM 标准型 S5 | 4 核 8G | ¥200–320 |
| 数据备份 | 对象存储 COS 标准存储 | 按量，几 GB | ¥1–5 |
| 域名解析 | DNSPod（免费版够用） | — | ¥0 |
| HTTPS 证书 | SSL 证书（免费 DV）或 Caddy 自动签发 | — | ¥0 |

**起步推荐**：Lighthouse 4 核 8G。Lighthouse 比 CVM 便宜、控制台更简单、含固定流量包，适合校级规模；日活突破 2000 或需要弹性伸缩时再升 CVM。

### 10.2 备案（关键前置，务必先办）

- 腾讯云主机 + 国内域名对外提供服务，**必须完成 ICP 备案**，否则 80/443 会被拦截。
- 备案周期通常 **7–20 个工作日**，是迁移的关键路径，**建议第一步就启动**，与开发并行。
- 小程序上线也要求服务器域名已备案且在微信后台配置为合法域名（见 11.3）。
- `api.pydaydayup.xyz` 若此前挂在境外（Vercel/CF），迁到腾讯云需重新走备案接入。

### 10.3 相比第四节的差异

第四节的迁移步骤（systemd、Caddy、切流量、回滚）**完全适用于腾讯云**，仅两点替换：
- 服务器创建改为在腾讯云控制台开 Lighthouse 实例；
- 备份目标从"OSS/R2"改为**腾讯云 COS**（`coscmd` 或 `cos-go-sdk` 上传每日 `.backup`）。

## 十一、微信小程序适配方案

蔚小芯已有 Flutter（Web + Android APK）前端。小程序是**新增端**，不替换现有端；后端 API 绝大部分可直接复用，仅需针对微信生态补三处。

### 11.1 前端技术选型（三选一）

| 方案 | 说明 | 取舍 |
|------|------|------|
| **原生小程序 / Taro / uni-app**（推荐） | 重写小程序 UI，直连现有 Go API | 体验最佳、审核最稳；需维护第二套 UI |
| Flutter 编译到小程序 | 复用现有 Flutter 代码 | 生态不成熟、包体大、审核风险高，不推荐 |
| WebView 套壳 | 小程序内嵌 `wxx-agent.pages.dev` | 最省事但微信对纯 WebView 套壳审核趋严，有驳回风险 |

**建议**：用 **uni-app 或 Taro** 新写小程序端，复用后端 API 与业务逻辑，只重做视图层。

### 11.2 后端要新增的：微信登录（`wx.login` → 换取 openid）

现有登录是学号/密码（`authH.Login`）。小程序需补一条**静默登录**链路，与现有 JWT 体系打通：

1. 小程序端 `wx.login()` 拿到临时 `code`；
2. 新增后端公开路由 `POST /api/v1/auth/wx-login`，用 `code` + 小程序 AppID/AppSecret 调微信 `jscode2session` 换 `openid`/`unionid`；
3. 按 `openid` 查/建用户（首次需绑定学号完成实名），**复用现有 `middleware.GenerateToken` 签发同一套 JWT**；
4. 后续请求沿用现有 `Authorization: Bearer` 鉴权，**RBAC/能力体系零改动**。

落地时需同步改两处（本项目已有对应位置）：
- `server/pkg/app/app.go` 的 `authGroup` 内注册 `authGroup.POST("/wx-login", ...)`（与 `qr-login` 同级，公开路由）；
- 若小程序经 CF Functions 代理，需把 `/api/v1/auth/wx-login` 加入 `frontend/functions/api/[[route]].js` 的 `PUBLIC_PATHS` 白名单（与现有 `qr-login` 等并列）。AppSecret 存服务器环境变量，**绝不下发前端**。

### 11.3 微信后台域名白名单（硬性要求）

小程序只能请求 **HTTPS + 已在微信公众平台配置的 request 合法域名**：
- 在「小程序管理后台 → 开发 → 开发管理 → 服务器域名」把 `https://api.pydaydayup.xyz`（或直连后端域名）加入 **request 合法域名**；
- 该域名**必须已 ICP 备案**（呼应 10.2）；
- 域名每月可改次数有限，上线前一次配好。

### 11.4 合规与审核要点（小程序比 App 更严）

- **隐私政策与用户协议**：项目已有 `RequireConsent` 同意门槛（`SEC-02`），小程序需在《小程序用户隐私保护指引》中如实声明收集的学号、对话内容等，并在微信后台填报。
- **实名与未成年人保护**：涉及学生（可能含未成年）数据，需按微信要求做合规声明。
- **内容安全**：用户输入与 LLM 输出建议接入微信 `msgSecCheck/内容安全` 或沿用现有 `middleware.PIIMask` + 内容过滤，避免违规内容导致小程序被封。
- **类目资质**：教育类小程序可能需要学校授权/办学资质证明，注册主体建议用学校或社团官方主体。

### 11.5 复用与新增一览

| 能力 | 小程序是否复用 | 说明 |
|------|---------------|------|
| 业务 API（问答/知识/办事等） | ✅ 全部复用 | 同一套 Go 后端 |
| JWT 鉴权 + RBAC | ✅ 复用 | 微信登录换发同一 JWT |
| 限流/配额/PII 脱敏 | ✅ 复用 | 中间件层，与端无关 |
| 登录方式 | ➕ 新增 `wx-login` | 静默登录 + 首次绑定学号 |
| 前端 UI | ➕ 新增 | uni-app/Taro 重做视图 |
| 域名合规 | ➕ 新增 | 备案 + 微信合法域名配置 |

### 11.6 建议实施顺序

1. **先备案**（10.2）——最长路径，立即启动；
2. 完成后端迁移腾讯云（第四节步骤，跑通现有 Web/APK）；
3. 后端加 `wx-login` 链路（11.2），本地联调；
4. uni-app/Taro 搭小程序骨架，接入登录与核心问答；
5. 配微信合法域名、填隐私指引、提交审核；
6. 灰度发布，逐步开放功能。
