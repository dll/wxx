## 二、架构与代码质量

### 2.1 项目结构

#### 🔴 问题 A1：Handler 层直接依赖数据库，违反分层架构

- **严重程度**：高
- **涉及文件**：
  - [education_handler.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/handler/education_handler.go)
  - [study_plan_handler.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/handler/study_plan_handler.go)
- **问题描述**：新增的两个模块直接在 handler 中持有 `*sql.DB` 并手写 SQL，违反了项目约定的"handler 只做参数校验和响应组装"分层规则。与其他模块（如 kb、user）的架构不一致，技术债快速堆积。
- **改进建议**：
  - 抽取 `EducationService`、`StudyPlanService` 到 service 层
  - 对应创建 `EducationRepo`、`StudyPlanRepo` 到 repository 层
  - 后续新增模块必须遵循三层架构，可加 CI 检查防止回归

#### 🟠 问题 A2：`app.go` 函数过长，职责过重

- **严重程度**：中
- **涉及文件**：[app.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/pkg/app/app.go)
- **问题描述**：`initAppWithConfig` 约 210 行，`setupRouter` 约 500 行，一个文件集中所有依赖初始化和路由注册，可读性和可维护性差。
- **改进建议**：
  - 按业务模块拆分路由注册函数（`authRoutes()`、`chatRoutes()`、`adminRoutes()`）
  - 使用依赖注入容器或 Wire 工具管理依赖
  - 将数据库初始化、迁移执行等拆分为独立函数

#### 🟠 问题 A3：权限中间件边界模糊，存在循环依赖风险

- **严重程度**：中
- **涉及文件**：
  - [auth/middleware.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/auth/middleware.go)
  - [middleware/jwt.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/middleware/jwt.go)
- **问题描述**：`auth` 包依赖 `middleware` 包的 `GetUserContext`，而 middleware 中也定义了 JWT 相关逻辑。权限代码散落在两个包中，边界模糊。
- **改进建议**：
  - 将 `UserContext` 模型移到 `model` 包
  - 将 `JWTAuth` 中间件移到 `auth` 包，统一权限相关代码
  - 明确：middleware 只放通用中间件骨架，auth 放鉴权具体实现

### 2.2 代码质量

#### 🔴 问题 A4：API 响应格式不统一

- **严重程度**：高
- **涉及文件**：`internal/handler/` 下所有 handler
- **问题描述**：
  - 成功响应有些使用 `gin.H{"code":0, "message":"...", "data":...}` 内联构造
  - 有些使用自定义结构体，有些直接返回数组
  - 错误响应格式也不统一
- **改进建议**：
  - 定义统一的 `ApiResponse` 结构体（含 code/message/data/trace_id）
  - 提供 `Success(c, data)`、`Fail(c, code, msg)` 等工具函数
  - 所有 handler 统一使用该工具函数返回

#### 🟠 问题 A5：日志使用标准库 `log`，缺少结构化与级别控制

- **严重程度**：中
- **涉及文件**：26 个文件使用 `log.Printf`
- **问题描述**：
  - 没有日志级别（debug/info/warn/error）
  - 没有结构化日志字段（trace_id、user_id 等）
  - Config 中有 `LogLevel` 字段但未实际使用
- **改进建议**：
  - 引入结构化日志库（`slog` 或 `zap`）
  - 统一日志格式，包含 trace_id、user_id、请求路径等上下文
  - 按配置的 LogLevel 控制输出

#### 🟠 问题 A6：审计日志异步写入可能丢失

- **严重程度**：中
- **涉及文件**：[middleware/audit.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/middleware/audit.go)
- **问题描述**：审计日志使用 `go func()` 异步写入，服务优雅关闭时未等待 goroutine 完成，可能导致请求审计日志丢失。高并发下 SQLite 单连接也可能成为瓶颈。
- **改进建议**：
  - 使用带缓冲的 channel + worker pool 模式
  - 注册 shutdown hook 等待队列排空
  - 考虑异步批量写入以提升性能

### 2.3 数据库设计

#### 🟠 问题 A7：动态 SQL 拼接白名单校验不统一

- **严重程度**：中
- **涉及文件**：
  - [user_repo.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/repository/user_repo.go)
  - [graduation_repo.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/repository/graduation_repo.go)
- **问题描述**：动态排序列名、表名使用 `fmt.Sprintf` 拼接。部分文件有白名单校验，部分没有。删除用户时遍历表名数组直接拼接 SQL。
- **改进建议**：
  - 所有动态列名/表名必须经过白名单校验
  - 封装通用的 `safeOrderBy(column, allowed []string)` 工具函数
  - `BatchDelete` 表名数组定义为常量，禁止外部输入

#### 🟠 问题 A8：外键约束不一致

- **严重程度**：中
- **涉及文件**：`migrations/` 目录
- **问题描述**：部分表有外键约束（sessions.user_id、messages.session_id），部分表没有（export_logs.user_id、feedback.user_id 等），一致性不足。
- **改进建议**：全面审查所有表的外键关系，确保引用完整性。

#### 🟡 问题 A9：迁移文件缺少回滚脚本

- **严重程度**：低
- **问题描述**：所有迁移文件只有正向 SQL，没有对应的回滚（down）脚本。
- **改进建议**：
  - 采用 goose 或 golang-migrate 等成熟迁移工具
  - 每个迁移配套 up 和 down 脚本

### 2.4 API 设计

#### 🟠 问题 A10：RESTful 风格不统一

- **严重程度**：中
- **涉及文件**：[app.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/pkg/app/app.go)
- **问题描述**：
  - 动作名端点：`POST /chat`、`POST /voice/asr`
  - 资源名端点：`GET /sessions`、`POST /kb/resources`
  - 批量操作路径风格不一
- **改进建议**：
  - 明确 REST 规范：资源用名词复数，动作通过 HTTP method 区分
  - 批量操作统一风格
  - 功能型端点（chat、asr）放在 `/actions/` 命名空间

## 三、安全性

### 3.1 认证与授权

#### 🔴 问题 S1：JWT 默认密钥弱，生产环境有被伪造风险

- **风险等级**：高危
- **涉及文件**：[config/config.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/config/config.go#L83-L83)
- **问题描述**：`JWT_SECRET` 默认值为 `"dev-secret-not-for-production-min-32-chars!!"`，如果生产环境忘记配置环境变量，会使用这个弱默认值。虽然有长度警告，但仅 warn 不阻止启动。
- **利用场景**：攻击者知道或猜到默认密钥后，可伪造任意用户的 JWT Token，直接越权登录。
- **修复建议**：
  - release 模式下如果 `JWT_SECRET` 为空或使用默认值，直接 panic 阻止启动
  - 开发环境才可使用默认值
  - 密钥长度检查在生产模式下强制生效

#### 🔴 问题 S2：缺少 API 速率限制，接口可被滥用

- **风险等级**：高危
- **涉及文件**：`internal/middleware/` 目录（无 rate limit 实现）
- **问题描述**：
  - 登录接口无限流，可被暴力破解密码
  - 聊天接口无限流，可能被刷爆 LLM 配额
  - 短信验证码接口（如有）无限流，可被刷短信费用
- **利用场景**：
  - 暴力破解：对登录接口每秒 100 次尝试密码
  - 费用滥用：聊天接口无限制调用产生高额 API 账单
- **修复建议**：
  - 实现基于 IP 的全局限流（如 100 req/min/IP）
  - 登录接口单独限流（5 次/分钟/IP）
  - 聊天接口按用户限流（60 次/分钟/用户）
  - 使用 `golang.org/x/time/rate` 或 `gin-contrib/ratelimit`

#### 🔴 问题 S3：日志明文记录短信验证码

- **风险等级**：高危
- **涉及文件**：[auth_service.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/service/auth_service.go#L63-L63)
- **问题描述**：短信验证码在日志中明文输出。
- **利用场景**：日志泄露后（如日志文件权限不当、日志服务漏洞），攻击者可读取验证码直接绕过认证。
- **修复建议**：
  - 生产环境禁止输出验证码明文
  - 调试级别日志输出验证码需脱敏（如前两位 + ***）
  - 统一日志敏感字段脱敏工具

#### 🟠 问题 S4：JWT 缺少刷新机制和吊销机制

- **风险等级**：中危
- **涉及文件**：[middleware/jwt.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/middleware/jwt.go)
- **问题描述**：
  - 只有 access token，没有 refresh token 机制
  - JWT 一旦签发，过期前无法吊销（修改密码、登出等场景）
  - 默认过期时间 2 小时偏长
- **修复建议**：
  - 实现 refresh token 机制（access 15min + refresh 7天）
  - 维护 token 黑名单或使用用户版本号机制
  - 支持主动登出功能

#### 🟠 问题 S5：数据范围权限未在中间件层统一校验

- **风险等级**：中危
- **涉及文件**：各 service/repository
- **问题描述**：能力授权在中间件层完成，但数据范围（owner_scope）散落在各 repository/service 中，容易遗漏导致越权。
- **修复建议**：
  - 设计统一的数据权限中间件或 service 层基类
  - 在 repository 层封装 `WithScope` 查询条件构建器
  - 确保所有列表查询自动应用 scope 过滤

### 3.2 AI/LLM 安全

#### 🔴 问题 S6：LLM 调用无限流配额，可能产生高额费用

- **风险等级**：高危
- **涉及文件**：[chat_service.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/service/chat_service.go)
- **问题描述**：
  - 聊天接口没有按用户/按天的调用次数限制
  - 没有 token 使用量配额管理
  - 缺少费用监控和告警
- **利用场景**：恶意用户或程序漏洞导致短时间内大量调用 LLM API，产生高额费用。
- **修复建议**：
  - 实现用户级别的日/月调用配额
  - 接入 token 使用量统计和费用预估
  - 设置费用阈值告警，超阈值自动降级或暂停

#### 🟠 问题 S7：Prompt 注入防护不足

- **风险等级**：中危
- **涉及文件**：[chat_service.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/service/chat_service.go)
- **问题描述**：
  - 系统提示词与用户输入直接拼接，缺少 Prompt 注入防护
  - 用户可以通过"忽略之前的指令"等方式绕过系统约束
  - 知识库内容也可能包含注入攻击（间接注入）
- **修复建议**：
  - 实现输入侧的注入检测（关键词、特殊模式）
  - 系统提示词使用 XML 标签或特殊分隔符隔离
  - 对检索到的知识库内容也做安全检查
  - 关键场景（如管理操作）增加人工确认

#### 🟠 问题 S8：内容过滤仅靠关键词匹配，易被绕过

- **风险等级**：中危
- **涉及文件**：[util/content_filter.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/util/content_filter.go)
- **问题描述**：
  - 基于简单的 `strings.Contains` 关键词匹配
  - 容易被谐音、拆字、空格插入、生僻字替换绕过
  - 容易误判（如"如何防范校园欺凌"命中欺凌关键词）
- **修复建议**：
  - 增加变体检测：拼音匹配、形近字、常见谐音替换
  - 引入 LLM 做内容安全二次校验（对高风险内容）
  - 区分主动询问和被动描述的语境
  - 建立误报反馈机制

### 3.3 输入验证与注入

#### 🟠 问题 S9：动态 SQL 拼接风险

- **风险等级**：中危
- **涉及文件**：多个 repo 文件
- **问题描述**：排序列名、表名使用 `fmt.Sprintf` 拼接，部分缺少严格的白名单校验。
- **修复建议**：
  - 所有动态列名/表名必须经过白名单校验
  - 封装通用的安全 SQL 构建工具
  - 增加 SQL 注入专项测试

### 3.4 配置与密钥管理

#### 🟠 问题 S10：CORS 白名单硬编码且过宽

- **风险等级**：中危
- **涉及文件**：[middleware/cors.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/middleware/cors.go)

  - 没有根据 `APP_MODE` 动态调整

  - CORS 允许域名移到配置中（环境变量，逗号分隔）
  - 生产模式下严格匹配，debug 模式可放宽
  - 支持通配符子域名的安全匹配

## 四、AI 能力与检索

### 4.1 检索系统

#### 🔴 问题 AI1：FTS NEAR 查询语法兼容性问题

- **影响程度**：高
- **涉及文件**：[kb_repo.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/repository/kb_repo.go#L172-L186)
- **问题描述**：
  - `buildNearQuery` 中每个字后加了 `*` 通配符（如 `NEAR(奖* 学* 金*, 3)`）
  - SQLite FTS5 的 `NEAR()` 语法**不支持**在 NEAR 内部使用前缀通配符
  - 可能导致查询解析失败或退化为 OR 匹配，NEAR 阶段形同虚设
- **验证建议**：写一个单元测试验证 `NEAR(a* b*, 3)` 语法的实际行为
- **改进建议**：
  - 改为 `NEAR("奖" "学" "金", 3)` 精确字符邻近匹配
  - 或去掉 NEAR 阶段，改用 BM25 + 应用层字符级距离重排

#### 🔴 问题 AI2：FTS 使用 unicode61 单字分词，中文语义粒度不足

- **影响程度**：高
- **涉及文件**：
  - [001_init.sql](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/migrations/001_init.sql#L64-L72)
  - [kb_repo.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/repository/kb_repo.go)
- **问题描述**：
  - FTS5 使用 `tokenize='unicode61'`，对中文按单字切分
  - 虽然有三阶段查询策略，但本质仍是字符级匹配
  - 无法理解"国家奖学金"vs"奖学金"的语义包含关系
  - 对长尾查询、同义词、近义词的召回能力弱
- **改进建议**：
  - 短期：在应用层做中文分词（引入 `gojieba`），生成 token 后构造 FTS 查询
  - 中期：引入 SQLite FTS5 中文分词插件
  - 长期：补充向量检索（embedding）做混合检索，FTS 负责精确匹配，向量负责语义召回

#### 🔴 问题 AI3：意图路由仅靠关键词匹配，准确率有限

- **影响程度**：高
- **涉及文件**：[agent/router.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/agent/router.go)
- **问题描述**：
  - `classify` 方法使用简单的 `strings.Contains` 关键词匹配
  - 关键词数量有限（每个意图 10-20 个），覆盖不足
  - 没有语义理解能力
  - 多意图匹配时没有优先级权重
  - 意图顺序不固定（map 遍历），相同问题可能每次路由结果不同
- **改进建议**：
  - 短期：补充更多关键词，增加权重机制
  - 中期：引入 LLM 做意图分类（few-shot prompt），关键词匹配作为兜底
  - 长期：训练专门的意图分类模型，或使用 embedding 相似度匹配

#### 🟠 问题 AI4：相关性二次过滤语义理解有限

- **影响程度**：中
- **涉及文件**：
  - [kb_repo.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/repository/kb_repo.go#L230-L294)
  - [chat_service.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/service/chat_service.go#L845-L950)
- **问题描述**：
  - 基于中文二元词组（bigram）做匹配
  - 停用词表小（20 多个），覆盖不足
  - 没有考虑 IDF，常见词和稀有词权重相同
  - 阈值（0.15）为经验值，缺乏数据支撑
- **改进建议**：
  - 引入 TF-IDF 在应用层做二次精排
  - 扩充停用词表（100+）
  - 考虑引入同义词/近义词词典
  - 根据测试集数据调优阈值

#### 🟠 问题 AI5：去重仅基于 ID，缺少内容级去重

- **影响程度**：中
- **涉及文件**：[kb_repo.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/repository/kb_repo.go#L210-L225)
- **问题描述**：
  - `mergeResults` 仅按 `resource_id + version` 去重
  - 同一政策的不同表述、不同版本的相似内容无法识别
  - 可能导致用户看到多个高度相似的来源
- **改进建议**：

#### 🟠 问题 AI9：上下文管理简单（固定 6 条历史）

### 4.4 知识库管理

#### 🔴 问题 AI12：FAQ 自动入库跳过人工审核

- **影响程度**：高
- **涉及文件**：[chat_service.go](file:///e:/2025-2026/2025-2026-2/wxx/WXX/server/internal/service/chat_service.go#L761-L794)
- **问题描述**：FAQ 自动入库直接 published，跳过了人工审核流程。如果 LLM 生成了错误的 FAQ，会直接进入知识库被检索到，产生错误答案，形成"错误自我强化"。
- **改进建议**：
  - FAQ 自动入库状态设为 pending，需人工审核后才 published
  - 增加入库前自动质检：敏感词扫描、重复检测
  - 建立知识质量评分机制，低质量内容自动降级

#### 🟠 问题 AI13：知识更新机制不完善，缺乏定期复审

- **影响程度**：中
- **问题描述**：
  - 缺少定期复审机制：政策类知识到期前应自动提醒复审
  - 没有变更日志：修改记录不可追溯
  - `expired_at` 存在但系统不会自动处理过期知识
- **改进建议**：
  - 增加知识生命周期管理：设置复审周期，到期前自动提醒
  - 实现知识版本历史，支持版本对比和回滚
  - 增加定时任务：扫描过期资源，自动标记或通知

#### 🟠 问题 AI14：反馈闭环不完整

- **影响程度**：中
- **问题描述**：
  - 用户反馈"回答有误"时，只触发 FAQ 缓存失效
  - 原始知识资源不会因反馈被标记或提醒
  - 缺少反馈数据统计和分析
- **改进建议**：
  - 建立反馈→知识改进闭环：高频错误知识自动进入复审队列
  - 增加反馈分析仪表盘
  - 反馈处理时支持直接关联并修改相关知识

### 4.5 评估机制

#### 🟠 问题 AI15：评测维度浅，缺少关键指标

- **影响程度**：中
