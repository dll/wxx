## 1. 阶段定位与目标

### 1.1 定位

第二阶段在 P0/P1 核心链路已完成的基础上，聚焦三件事：

1. **创新落地** — 多智能体编排从"提示词切换"升级为真正的 Eino 协同
2. **安全合规** — 补齐隐私政策、PII 脱敏、内容过滤等合规底线
3. **角色闭环** — 六级 RBAC 每个角色都有完整、差异化的功能体验

**本阶段不包含校外系统对接**（学工/一表通/SSO），这些作为第三阶段独立排期。

### 1.2 目标

| 维度 | 第二阶段目标 |
|------|-------------|
| 创新 | Eino 多智能体编排最小可用版（3 Agent 协同 + 结果汇聚） |
| 合规 | 隐私政策/用户协议/授权弹窗/PII 脱敏/内容安全过滤全部就位 |
| 质量 | 建立 200 条评测基线，核心 KPI 可测量 |
| 角色 | 六级角色各功能端到端验证通过，扩展 teacher/assistant 枚举占位 |
| 导出 | PDF + PNG 长图导出可用，带水印与审计 |
| 运营 | 学生会运营组搭建，知识库扩充至 50+ 条 |
| 体验 | 个性化推荐增强、情感预警调优、前端动效打磨 |

## 3. 专项一：多智能体 Eino 编排

### 3.1 现状

`internal/agent/` 仅有 `doc.go`（4 行包注释）。当前 ChatService 通过 `agentID` 从数据库加载不同 system prompt——本质上是**提示词模板切换**，不是多智能体协同。

### 3.2 目标

实现 Eino 编排的最小可用版：支持 2-3 个 Agent 并行/串行协同 → 结果汇聚 → 统一回复。

### 3.3 技术方案

```text
+----------------------------------------------------------+
| FIG 3.3  EINO MINIMAL ORCHESTRATION                       |
|                                                          |
|  POST /chat { question, agentID? }                       |
|       |                                                  |
|       v                                                  |
|  [Intent Router] ── 判断问题类型                           |
|       |                                                  |
|  +----+----+                                             |
|  |    |    |                                             |
|  v    v    v                                             |
| [QA] [Policy] [Process]  ← 并行调用                       |
|  |    |    |                                             |
|  +----+----+                                             |
|       |                                                  |
|       v                                                  |
|  [Result Merger] ── 去重 + 排序 + 冲突检测                  |
|       |                                                  |
|       v                                                  |
|  AnswerCard (含各 Agent 来源标注)                          |
+----------------------------------------------------------+
```

*图注：意图路由 → 并行调用多个子 Agent → 结果合并 → 统一 AnswerCard。*

### 3.4 实施步骤

| 步骤 | 内容 | 产物 |
|------|------|------|
| 1 | 定义 Agent 接口：`Execute(ctx, question, context) → AgentResult` | `internal/agent/interface.go` |
| 2 | 实现 3 个子 Agent：QA（通用问答）、Policy（政策检索）、Process（流程引导） | `internal/agent/qa_agent.go` 等 |
| 3 | 实现 Intent Router（基于关键词 + 规则，初期不依赖 LLM） | `internal/agent/router.go` |
| 4 | 实现 Result Merger（去重 sources、冲突检测、优先级排序） | `internal/agent/merger.go` |
| 5 | 集成到 ChatService：`agentID == ""` 时走默认多 Agent 协同 | `internal/service/chat_service.go` |
| 6 | 单元测试：Router / Merger / 各 Agent 独立测试 | `internal/agent/*_test.go` |

### 3.5 关键设计决策

- **初期不用 Eino Graph/Workflow**：先用 Go channel + goroutine 做并行编排，封装为清晰的接口。待 Eino 稳定 tag 确认后再替换底层实现，接口不变。
- **Router 用规则而非 LLM**：减少延迟和成本。规则覆盖 8 个业务域关键词，后续可扩展为 LLM 分类器（P3）。
- **Merger 的冲突策略**：不同 Agent 返回冲突结论时，优先 Policy Agent 的条款原文，并标注"存在不同解读"。

## 4. 专项二：安全合规补齐

### 4.1 隐私政策与用户协议

| 步骤 | 内容 | 文件 |
|------|------|------|
| 1 | 撰写《蔚小芯隐私政策》（数据收集范围、使用目的、存储期限、用户权利） | `docs/privacy-policy.md` |
| 2 | 撰写《蔚小芯用户协议》（服务范围、免责声明、行为规范） | `docs/user-agreement.md` |
| 3 | Flutter 首次启动弹出授权弹窗（隐私政策 + 用户协议勾选确认） | `frontend/lib/widgets/consent_dialog.dart` |
| 4 | 情感分析功能独立授权弹窗（在首次使用语音/情感功能时触发） | 同上组件复用 |
| 5 | API 返回授权状态标记（`UserProfile.consentStatus`） | `server/internal/handler/auth_handler.go` |
| 6 | 未授权用户禁止使用问答/语音/情感功能 | `server/internal/middleware/consent.go` |

### 4.2 PII 脱敏

| 步骤 | 内容 |
|------|------|
| 1 | 实现脱敏工具函数：学号（保留前 4 + 后 2）、手机号（保留前 3 + 后 4）、身份证（保留前 6 + 后 4） |
| 2 | 在 `chat_service.go` 中 LLM 调用前对用户问题做脱敏 |
| 3 | 在 `emotion_handler.go` 中分析前对输入文本做脱敏 |
| 4 | 脱敏日志：记录脱敏前后 hash，不记录明文 |

### 4.3 内容安全过滤

| 步骤 | 内容 |
|------|------|
| 1 | 定义敏感词库（政治敏感、色情暴力、违法信息三类，初始化 ≥ 100 词） |
| 2 | 实现 `internal/util/content_filter.go`：关键词匹配 + 规则过滤 |
| 3 | 在 LLM 返回后、构造 AnswerCard 前执行过滤 |
| 4 | 触发过滤时返回兜底回复："抱歉，该问题涉及的内容暂不支持回答" |
| 5 | 过滤事件写入审计日志（traceId + 触发词类别，不记录具体词） |

## 5. 专项三：多格式导出体系

### 5.1 现状

`GET /api/v1/export` 端点存在，但仅实现了 NDJSON 知识导出。文档要求的 PDF/Word/PNG/Excel/ICS/MD/JSON 多格式导出未实现。且文档中规定的方法是 `POST`，实际为 `GET`。

### 5.2 实施内容

| 步骤 | 内容 |
|------|------|
| 1 | 修正路由：`GET /api/v1/export` → `POST /api/v1/export`（与 API 契约一致） |
| 2 | 新增 `/kb/export`（GET，知识包导出，分页 + cursor） |
| 3 | 新增 `/kb/validate`（POST，包校验） |
| 4 | 实现 PDF 导出（Go 端生成，含标题/时间/版本号/水印/sources 脚注） |
| 5 | 实现 PNG 长图导出（Flutter 端截图 + 拼接，用于活动通知一键分享） |
| 6 | 实现导出审计日志（导出人/角色/时间/格式/是否含敏感字段/traceId） |
| 7 | 学院/学校级导出增加水印 + 二次确认对话框 |
| 8 | Flutter 导出 UI（AnswerCard 底部"导出"按钮 → 格式选择 → 下载/分享） |

### 5.3 技术选型

| 格式 | 实现方式 | 说明 |
|------|----------|------|
| PDF | Go: `go-pdf` 或 `gofpdf` | 服务端生成，支持中文 |
| PNG 长图 | Flutter: `RepaintBoundary` + `dart:ui` | 客户端截图拼接 |
| Word | 暂缓（P3） | 需模板引擎，工作量大 |
| ICS | 暂缓（P3） | 日历订阅非高频需求 |

## 11. 专项九：性能与稳定性

### 11.1 压测

| 步骤 | 内容 |
|------|------|
| 1 | 编写压测脚本（模拟 50/100/200 并发用户，混合场景：问答 + 知识浏览 + 导出） |

| 3 | 配置延迟告警（P95 > 3s → 通知） |
